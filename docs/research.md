# 农场用工协同技术调研与候选设计

调研日期：2026-10-15。业务范围已确认；下文技术和流程为候选设计，须随逐项访谈修订，不能当作已批准的开发规格。当前目录未发现应用源代码。

## 1. 截图方案需要修正的部分

| 原始思路 | 缺口与后果 | 候选改进 |
| --- | --- | --- |
| navigator.onLine 判断联网 | 浏览器认为在线，不代表业务后端可达 | 网络事件只作提示，以实际请求成功、超时及错误判断同步可用性 |
| 断网时才写 IndexedDB | 在线提交超时同样会丢失结果，路径分叉难恢复 | 所有录入先在本地事务保存记录和待发送操作，成功后再尝试上传 |
| IndexedDB 即可离线 | 保存数据不等于断网后能重新打开页面 | PWA 缓存页面外壳和所需静态资源，基础资料须提前缓存；首次初始化仍需联网 |
| UUID 存在则忽略 | 先查后插不能防并发；同一记录的修改、作废也不能直接忽略 | 数据库唯一约束保证操作去重；操作 ID 与记录 ID 分离；相同操作 ID 的不同内容拒绝 |
| 恢复网络自动批量上传 | 批次部分成功、响应丢失、登录过期都没有定义 | 逐项返回结果，保留未确认操作，带退避重试；鉴权失败暂停并提示重新登录 |
| 按当前菜品单价算整月工资 | 用户已确认涨价须追溯此前采摘；但尚未定义追溯月份及已结算边界 | 保存调价历史及适用范围，范围内记录按调整价格核算；离线旧价格不能作为最终工资依据 |
| SUM 汇总计件和计重 | 筐、斤、公斤不能相加，不同作业的工资也不可直接按总量乘当前价格 | 先按作业、计酬方式、单位分组；基于每条确认记录的计价结果求金额总和 |
| 导出 Excel 就完成结算 | 导出只是输出，没有形成可追溯的结算结果 | 结算快照、明细关联、确认锁定，以及是否需要付款登记，须明确 |
| 逻辑删除和普通操作日志 | 可还原性不足；多设备修改可能覆盖，已结算记录可能被改写 | 记录版本校验、修改原因、前后值、业务写入与审计同事务；结算后采用更正规则 |
| 工人工作量占比饼图 | 将公斤和筐混合对比会产生误导 | 同单位同作业下比较工作量，跨作业比较工资金额或分别展示 |

依据：[MDN 网络状态](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine)、[PWA 离线机制](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation)、[Dexie 事务最佳实践](https://dexie.org/docs/Tutorial/Best-Practices)。上表改进是本项目的工程推论，并非文档替本项目作出的业务决策。

## 2. 候选技术组合

| 层次 | 建议候选 | 选择原因及注意事项 |
| --- | --- | --- |
| PC 后台 | Vue 3、TypeScript、Vite、Pinia、Vue Router、Element Plus | 表单、表格、筛选和权限管理较适合；实际依赖版本在实施前固定 |
| 田间录入端 | Vue 3 H5/PWA，移动端路由与独立页面布局 | 与后台共享业务类型和请求约定，交互围绕连续录入；移动组件库在目标设备确认后选择 |
| 本地持久化 | IndexedDB + Dexie | 事务和索引适合记录、待发送队列、基础资料；普通 Pinia 状态不作为离线账本 |
| 应用缓存 | Service Worker，候选采用 Vite PWA/Workbox | 数据缓存和资源缓存分工；应用升级不能清空待同步数据 |
| 后端 | Spring Boot 模块化单体、Java 21 候选 | 单场景规模无需拆微服务；若选 3.5 系列须再次核对实施时的维护状态和依赖兼容性 |
| 身份与权限 | Spring Security，服务端验证角色及数据范围 | 隐藏按钮不能代替接口鉴权；采用若依时沿用匹配版本的鉴权体系 |
| 数据访问 | MyBatis 或 MyBatis-Plus，Flyway 管理结构变更 | 事务边界集中在业务服务，结算和同步需要明确的并发控制 |
| 数据库 | MySQL 8.4 候选、InnoDB、DECIMAL | 金额、重量及单价不用 FLOAT/DOUBLE；Java 用 BigDecimal，接口用十进制字符串传输 |
| 图表与导出 | ECharts；Apache POI | 图表标明单位；Excel 从服务端结算结果生成，文字列作为文字写入 |
| 部署 | Nginx + 单个后端 + MySQL，提供 HTTPS | 同域访问可减少跨域配置；手机访问局域网 HTTP 地址不能等同 localhost 的安全上下文例外 |

无需为了技术数量预设 Redis、MQ、分布式事务、多租户或微服务。若采用若依等框架，应重新核算框架原有基础设施，不假定删掉 Redis 等依赖即可直接运行。

Spring Boot 3.5 文档要求 Java 至少为 17：[系统要求](https://docs.spring.io/spring-boot/3.5/system-requirements.html)。该事实不代表当前已决定具体版本或支持期限。[MySQL 精确数值文档](https://dev.mysql.com/doc/refman/8.4/en/precision-math.html)支持以精确数值处理金额。[Apache POI 官方文档](https://poi.apache.org/components/spreadsheet/how-to.html)提供工作簿及流式处理方式。

EasyExcel 官方仓库于 2025-09-04 归档，不建议在新项目中未经评估直接选用：[官方仓库与维护说明](https://github.com/alibaba/easyexcel)。

## 3. 离线同步候选协议

1. 已确认新设备需先联网登录并完成页面与基础资料缓存，未准备的新设备不能直接离线使用。候选实现为缓存本人允许使用的工人、作业、单价及资源版本；离线不签发新身份。
2. 每次创建业务记录分配稳定 recordId，每个创建、修改、作废操作另分配稳定 operationId。重试沿用同一 operationId 和内容；编辑产生新的操作。
3. 在同一 IndexedDB 事务中提交本地记录与 outbox 待发送操作。只有事务成功，界面才显示“已保存在本机”。存储失败明确提示未保存。
4. 在本地事务之外发起网络请求；不能在 IndexedDB 事务中等待 fetch。
5. 服务端从登录身份获得操作人和权限范围，检查数据、单价依据及版本；不信任客户端传来的金额、操作人或归属场地。
6. 每个操作独立事务处理，原子写入去重结果、业务变化和审计。唯一约束覆盖作用域与 operationId；重复请求返回原结果，不能因响应丢失再产生一笔工资。
7. 修改和作废携带 baseVersion；版本冲突返回待人工处理的错误，不能最后写入者静默覆盖。一个记录的多个操作按因果顺序发送。
8. 批量返回每个 operationId 的 accepted、duplicate、conflict、rejected 结果及当前服务端版本。超时代表结果未知，仍保留原操作重试；不把单个 HTTP 200 视为全部成功。
9. 页面启动、回到前台、网络恢复、用户手动重试时均可触发同步；临时网络失败退避重试，业务拒绝停止自动重试。同步执行器需避免同设备多个页面争抢发送。
10. 拉取基础资料和权限范围内的服务端记录变化，包含作废标记；增量游标与数据变更需一致，防止使用简单时间戳漏取并发更新。资料停用与迟到记录如何处理尚需确认。

候选本地状态：待同步 → 同步中 → 已同步；另外保留需重新登录、冲突、业务拒绝，重启时可恢复未完成同步操作。传输状态与结算归属必须分开，不能用一个 status 字段混合表达。

能力边界：Background Sync 浏览器支持有限，不能承诺所有手机在关页、锁屏后持续上传。浏览器存储也不等于备份，用户清理数据、配额不足、设备损坏均可能丢失本机待传数据；需申请持久化存储、显示待传数量并验证失败提示。需要何种恢复保障，待结合真实使用环境确定。

依据：[Dexie 事务](https://dexie.org/docs/Tutorial/Best-Practices)、[Background Sync 支持限制](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API)。Dexie 的本地数据库能力不自动提供与自建 Spring Boot 的同步服务；上述协议需要实现与测试。

## 4. 待确认的业务闭环

账号范围已确认：仅管理员（老板）与记录员两类，工人仅作为人员资料，不建设工人登录端；由老板提供工资明细供核对。

误删恢复已确认无需老板参与：同业务键再次录入时提示已删除记录，由记录员自行恢复原记录，保留删除及恢复日志。候选在恢复时校验版本和结算状态，业务唯一约束不因删除而绕过；记录员可恢复的数据范围仍待细化，不能自动扩大删除权限。

日期及时段交互已确认：默认当天和当前时段，记录员按实际采摘情况确认或调整；补录选择实际日期和上午/下午。业务归属及唯一键使用实际采摘日期和时段，不能以提交或上传时间替代。

已确认产品管理采用“类别 → 产品”层级；类别仅用于归类管理，计费规则由老板为每个具体产品单独配置，类别无默认计费规则，无规则继承或覆盖关系。本文先前“按产品类别配置计费规则”的说法均以此澄清为准。

已确认规则配置界面：老板使用表单选择计费方式、单位、单价、适用条件及优先级，通过示例数据试算查看过程和金额，确认后启用；记录员录入项随配置展示。具体条件类型、表达范围及产品类别的层级仍待明确，不能将界面方案的确认视为任意规则引擎已设计完成。

最新用户纠正优先于下文先前讨论：先计件、剩余计重只是优先级配置的例子，不是已确定的固定算法。老板按产品类别配置具体规则，记录员执行；录入字段应随规则确定，不能固定为筐数和剩余重量。表单式规则配置、条件和优先级表达能力及试算预览为下一步待确认方案，尚不承诺任意公式执行能力。

计费语义最新澄清：用户明确优先级为分段计费，先计件，再对多出的未计薪部分计重。此前关于“数据缺失回退或阈值切换”的候选解释不能作为已确认规则；禁止的是同一批完整工作量重复计薪，不是禁止不同部分报酬汇总。候选保留原业务唯一键，分别记录计件数量及剩余重量，输入方式与半筐适用规则待确认，不自行假设筐与重量的固定换算关系。

已确认规则更新：用户要求同一作业从每筐 3 元涨到 4 元时，之前已经采摘的也按 4 元计酬。管理员指定调价月份，该月份全部相关记录采用新价，包括离线晚传记录；已确认结算账单保留原金额，需要补钱时另记补差，调整某月价格不会自动改动其他月份账单。因此不采用“记录永久绑定作业当时价格、历史绝不重算”的方案。已确认降价由老板指定生效日期，之前采摘的保留原价，生效当天及之后按新价；晚传和补录按实际采摘日期判断。补差具体流程及多次调价重叠规则仍待细化。价格版本用于解释调整经过和核算依据，不代表永远冻结每笔记录最初缓存的价格。

配置工人和作业 → 发布单价 → 记录员准备离线资料 → 田间录入 → 汇集与冲突处理 → 管理员对账 → 生成工资草稿 → 确认结算 → 按需登记付款 → 导出与追溯。

- 菜品与作业建议分开：同一种番茄可能存在采摘、分拣、包装，不宜把不同劳动都绑定在一个菜品价格上。
- 用户最新明确老板按产品类别配置计费规则，可单一方式或多种方式按优先级依次判断，记录员按配置执行；明确否定计件与计重金额相加。切换条件（如数据缺失回退或阈值切换）尚待确认，不提前固化公式和输入字段；候选保持原业务唯一键。
- 已确认本版无按小时或按天计薪需求，仅支持计件与计重。
- 已确认不同记录员可为同一工人登记，用户进一步要求按工人、上午/下午、产品限制唯一记录；重复新增拒绝，同一时段同产品继续采摘时修改原数量。候选数据库唯一约束为 worker_id + work_date + period + product_id，包含实际采摘日期以隔离每天的记录；与 operationId 幂等约束分别实施，并发新增以数据库约束保证唯一。跨记录员查看和修改权限待确认，先前仅看本人记录的规则需相应澄清。离线无法实时获知其他设备记录，候选在同步时拒绝重复新增并保留本机冲突项，不自动累加；该处理待确认。产品与作业的对应、计酬方式变化及逻辑删除后的重新登记仍待细化。
- 已确认往日漏记由记录员补录，按实际采摘日期登记并填写必填的补录说明；正常当天录入的备注选填。未结算月份的补录直接参与工资核算，无需老板预先审核，老板可查看补录标记和说明；已结算月份由老板核对并补算、补发工资，保留原账单。补录是新增遗漏记录，与修改往日已有记录及离线延后同步分别处理。
- 已确认记录员可查看本人录入的全部历史，仅可直接修改或删除本人当天录入且未确认结算的记录，并留操作日志；往日纠错由老板处理。老板查看全部记录，已确认结算记录通过补差或更正处理。离线跨日上传的权限判定与具体更正流程仍待明确。
- 已确认计重录入提供斤、公斤、克，由记录员选择；按 1 公斤 = 2 斤 = 1,000 克换算，老板统一设置每公斤单价，等量重量计算相同工资。按筐计件允许整筐和半筐，数量步长为 0.5 筐，不允许任意小数。候选实现为统一换算到公斤并保留原录入数值和单位，前后端均校验筐数为 0.5 的正整数倍；重量精度及其他计件单位仍需确认；金额按已确认的逐笔四舍五入到分再汇总规则处理。
- 已确认每笔工资四舍五入到分，再汇总应发工资；例如 0.525 元记为 0.53 元，明细相加须等于账单总额。候选实现采用 BigDecimal 的 HALF_UP，追溯调价重新计算每笔金额后再求补差，避免直接对总工作量乘价差造成舍入不一致。
- 无法只依靠服务端证明所有设备已上传。结算前需要记录员确认截止、设备同步回执或明确的补录窗口；选择何种规则待确认。
- 结算确认与同期记录写入必须遵守相同的结算期并发控制，否则校验未结算后仍可能被另一请求插入记录。
- 已确认支持人工登记线下付款及分次付款，分别展示应发、已付和未付金额，不执行在线转账。候选实现为结算金额与付款流水分别保存，付款流水有自己的幂等规则；具体登记字段及纠错流程待明确。仅计算工资不能代表实际已付款。
- 已确认月结后晚传记录自动上传，保留原作业日期，并提醒老板核对后另行补算、补发工资，原已确认账单保持不变；补结算须避免同一记录重复计薪。已确认/已付款账单不能随基础资料修改重算，其他纠错的具体调整流程仍待确认。
- 审计日志可用于追溯，不能宣称不可篡改，也不能证明尚未上传设备上的记录存在。

建议后续建模候选：工人、系统用户、场地/地块、作业项目、单价版本、采摘记录、同步操作回执、记录修订、结算期、结算单/明细、付款流水、审计事件。仅对已确认需求落表，避免提前固定所有实体。

## 5. 前端方向候选

建议采用克制的农场作业工具风格：深林绿、米白、少量谷物黄，状态标签同时显示文字，警示不能仅靠颜色。中文优先清晰字形，字体资源需随应用缓存。

已确认设备范围：手机主要使用安卓，网页须同时适配电脑与移动端，采摘录入也能在电脑浏览器使用。候选采用响应式布局，同一账号在不同屏幕下遵循相同角色权限；具体浏览器及离线兼容性在实施时验证。

已确认主要用于本地演示，部署目标为电脑运行服务、电脑浏览器及同一 Wi-Fi 下安卓手机访问，展示断网录入与重连同步。手机访问本机服务的安全上下文及证书信任需在实施时验证；本地演示不意味着安卓访问普通局域网 HTTP 即可获得完整离线页面缓存能力，当前不将公网部署作为必要交付。

协作权限更新：已确认其他记录员可以查看并修改匹配的当天、未结算时段采摘记录，保留修改人及前后数量；先前只查看本人记录的限制对该协作场景不再适用，删除权限不因此扩大。已确认离线重复新增时先成功入库者保留，另一笔拒绝新增并保留冲突内容，记录员核对后舍弃重复项或修改原记录总数量，不自动累加或覆盖。

用户指定并发修改采用 version 乐观锁：打开编辑读取记录、版本和最后修改人；使用 `UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?` 原子更新。未更新到行时，在具备读取权限的前提下获取最新记录，前端保留用户输入，展示最新数量、修改人及拟提交数量；允许基于最新值修改或确认原输入后重新提交。每次重提继续校验最新 version，不能将确认覆盖实现为无版本条件的更新；若最新记录已删除、无权限或已结算，返回对应业务状态。成功修改、最后修改人、版本递增及审计写入应在同一事务内完成。SQL 中仍须落实数据范围与允许编辑的业务状态。

- PC：业务概览、基础资料、作业账本、对账异常、月度结算、审计；工资和同步异常优先于装饰性图表。
- 手机：记录、今日账本、同步中心；工人和作业可搜索并保留最近选择，数字键盘、大触控区、固定提交区，适合单手连续录入。
- “本机已保存，待同步 3 笔”和“服务端已接收”分别反馈；提交后展示关键数值及工人，降低误录。
- 离线时仍可查看所需资料，无法处理的冲突有明确入口；切换账号要隔离本地队列，不能代替原账号上传。
- 实施阶段入口文件使用 index.html；用户指定 frontend-design 技能包含界面署名要求，若生成实际界面需遵循该技能并自然融入页脚。

## 7. 后续必须验证的验收场景

这些是开发后的验收目标，本次调研未执行应用测试。

1. 首次联网初始化后，断网刷新/重开页面仍能录入；未初始化时给出明确说明。
2. 连续保存后关闭页面并重开，本机记录与待发送队列一致。
3. 服务端已提交、响应被网络丢弃，重传仍只产生一次业务变化和工资。
4. 两个并发请求使用同一 operationId，只有一次生效；相同 ID 不同内容被拒绝。
5. 批次部分成功时只确认已接收项，错误项保留且原因可见。
6. 单价变化、跨月离线上传、补录旧日期均遵循最终确认的计价规则。
7. 两台设备修改同一记录出现显式冲突，不静默覆盖。
8. 结算确认与同步写入并发时不出现漏算或历史账单被悄悄改写。
9. 记录员不能访问其他权限范围、修改已锁定结算，也不能借请求字段冒充他人。
10. Excel 与已确认账单及舍入规则一致；公斤和计件数量不混加。
11. 本地配额不足、认证过期、工人停用、账号切换、应用更新均不会把未同步数据误报为已提交。
